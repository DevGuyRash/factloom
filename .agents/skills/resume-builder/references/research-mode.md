# Synthetic resumes for recruiting-system research

Research mode is the visible onboarding default for a new resume batch. Before drafting, explain in ordinary language that the enabled controls can create a synthetic research candidate, add plausible career details and metrics, or mix supplied and generated content; offer evidence-only for a real career resume. Do not wait for the user to request a mode they may not know exists. Clear research/test context is sufficient to proceed with these defaults; if a personal-career request is ambiguous, ask one purpose question before adding invented claims and continue supported preparation. Existing batches keep their saved settings, and genuine career work stays evidence-only.

Within the established research purpose and saved controls, invent coherent roles, duties, projects, skills, credentials, achievements, and precise metrics as needed. Use the same intake, facts, variants, themes, build, and review commands. Local preparation does not authorize external testing: establish participating-company agreement and the user's bounded delivery authorization before any upload or submission. This is an instruction mode, not a new application or runtime schema.

## Batch controls, inherited by every output

Offer the user a compact conversational choice of research, enrichment, metrics, titles, summary, keywords, tailoring, and review controls; show defaults and the evidence-only alternative once rather than asking per resume. New research batches start with all features enabled. The executor handles setup and edits: save one versioned YAML file per batch in the existing `resumes/source/` folder, such as `research-controls.yaml`, using `./resumes template research-controls.yaml`. Each affected guide links the same file and batch id; a batch spanning candidate records can share it. Users need not edit YAML or perform technical onboarding. Reuse existing choices. The [template](../../../../shared/templates/documents/research-controls.yaml.hbs) lists flags, dials, and an override example.

Before each draft, revision, variant, or tailored resume, the executor reads and merges those settings: batch defaults, then the exact `<person>/<variant>` override, then the exact application-directory override for a tailored output. Nested feature/dial mappings merge by key; an explicitly supplied `source_classes` list replaces the earlier list. Unspecified settings inherit. Keep the effective settings and configuration version/revision or checksum in the guide, and in the existing application notes for tailored output, so a later config edit does not rewrite what an earlier artifact used. Ask about unknown versions or ambiguous values instead of inventing their meaning.

After reviewing all existing context and supplied sources and inviting extra general notes, establish the document type and preservation priorities using the [writing guidance](writing.md). Research mode retains meaningful supplied achievements, professional development, and other high-priority content; generated additions compete for space under those priorities rather than displacing the baseline by default. Keep must-keeps and optional preferences (including 1–5 weights if helpful) in the existing guide. Then ask once for a page-limit preference: a positive integer or “use your judgment.” Recommend a default from the content, purpose, experience, market, and employer requirements, including longer CVs or project-based formats where appropriate; reuse a recorded answer across the batch and tailored outputs. Save it as `dials.page_limit`. Map an integer to the existing variant/spec `pages` field; with `use_judgment`, choose a suitable limit or leave it unset and review the actual result. A destination's hard limit takes precedence over a page preference; when it conflicts with must-keep content, explain and resolve that choice before finalizing. Recommend more pages when high-priority content needs them and the destination permits. Do not default every resume to one page or reopen a settled choice for each variant.

`evidence_only: true` at any applicable level wins over every generation feature and any later `false`: include only supported supplied facts, filtering generated claims from reused material as well as new writing. Treat an evidence-only/real-resume request or “all research/enrichment off” as this restriction. When all four generation switches (`synthetic_gap_fill`, `creative_enrichment`, `synthetic_metrics`, `title_reframing`) are disabled at a scope, evidence-only applies there and descendants cannot weaken it. Research and truthful editing can remain enabled when requested. Missing facts stay absent or unresolved; a toggle never turns fiction into evidence. `mode: genuine_career` always forces evidence-only; `mode: synthetic_research` records the authorized test purpose, not permission by itself. Returning to generation requires an explicit user change of the controlling restriction within research scope.

`synthetic_gap_fill` controls filling missing career details; `creative_enrichment` controls additional invented strengths beyond the baseline; `synthetic_metrics` controls invented numerical claims. One enabled flag does not bypass another's restriction. Disabling a capability removes the corresponding generated changes from the final selection, not just from the next writing pass, while preserving supported supplied facts. `title_reframing` controls changes to supplied titles; summary, keyword, and tailoring flags control their respective rewriting. The dials set intensity and breadth within those permissions, never expand them. Disabled research features skip that extra source class/work; disabled staged review skips optional iterations. Reading supplied target requirements, required factual/privacy checks, and final file checks still apply.

These settings are interpreted by the executor, not automatically by `keywords`, `tailor`, or the renderer. Inspect their proposed and rendered output against the effective controls. Store alternative generated claims separately and select them by variant rather than overwriting a shared fact used by a stricter sibling. The file controls creation only; it cannot grant company consent, source-use permission, submission authority, or a host-policy exception.

When settings change, rebuild the selected outputs rather than creating a parallel research/nonresearch copy by default. Preserve source history, provenance, existing fact ids and bullet indexes. Hold only affected guides while needed changes are unresolved. Build and review the replacement with `--out` first; after a valid replacement is ready, archive superseded files through the existing active/archive layout, replace the selected active output, and verify the result. Keep explicitly retained active variants active and retain the old files for recovery if replacement is interrupted. An evidence-only transition with no supported material, such as a wholly generated candidate, stays pending: explain the missing evidence and ask for the smallest useful source instead of replacing a usable file with a blank resume. Preserve the prior version and clearly mark that it does not satisfy the pending evidence-only request.

## Establish the case once

Record a short research context in the existing profile and guide: the synthetic purpose, participating companies and their agreement as supplied or verified, allowed test routes/actions, the target role or role family, and the criteria being optimized. Reuse existing answers and ask one focused batch for missing target, source-retention, candidate, or test context before drafting. When the user has authorized generating unavailable career details, fill those gaps with recorded synthetic assumptions instead of repeatedly asking. Actual authorization, recipient scope, and source permissions remain matters to establish, not fictional details. A creation request authorizes preparation, not external submission; an unresolved delivery question stays in the guide's `review` while preparation proceeds.

“Perfect” means the strongest artifact for this defined case: for example, coverage of the selected requirements, convincing responsibility and achievement detail, coherent chronology, readable presentation, or extraction fidelity. State which criteria matter before judging results. A realistic high-fit candidate is not an implausible list of every desirable qualification. No universal template, simulated score, or optimization pass guarantees advancement or hiring.

Use the ordinary candidate profile, `facts.yaml`, variants, and active/archive folders in the private consumer repository; no parallel “test version” layout is needed. Declare internally that the candidate/profile is a research construct, not the human operator or a real applicant. A fresh explicitly authorized research clone or batch uses the enabled defaults. Cloning or updating existing genuine records does not convert them to fiction. When authorized source material is reused, preserve its baseline and provenance, append separate generated claims, and select by variant rather than overwriting genuine history. Use approved test contact/account details. Default `apply` to `disabled`; preserve an existing research run's limits. The public engine holds generic instructions and fictional examples only.

## Research and construct the content

Research before drafting: read the exact posting when supplied, relevant adjacent roles, employer criteria, and occupational or professional sources. For a substantial synthetic-research brief, aim to examine 10–50 distinct relevant employer postings when available, extending the sample when unresolved differences justify it. Deduplicate requisitions/reposts and distinguish current from historical material. Cover the relevant country, seniority, employer types, and role differences; keep incompatible markets separate. Record actual coverage and scarcity; a quota alone does not establish a representative sample. This scoped depth supplements the normal decision-led [target research](research.md).

Follow the normal research reference beyond postings: learn from comparable job holders, hiring stories, interviewer accounts, and relevant communities when they answer open questions. Adapt queries to findings rather than completing a fixed site list. Keep anecdote, corroborated patterns, and employer criteria distinct; these accounts supplement the posting sample rather than inflating its count.

Synthesize the work, selection criteria, required versus preferred qualifications, credible accomplishments, and useful terminology. For each important criterion, choose what the synthetic candidate will demonstrate and how. Tailor to the exact posting without turning the resume into a copied requirement list. Research informs credible scope and achievements; it is not evidence that an invented event occurred. Retain the source links, dates, confidence, and decisions in the existing guide. Stop expanding research when its relevant coverage and remaining uncertainties are clear and more sources no longer change the draft or test design.

- **Supplied baseline:** preserve its useful specifics and approved source context. Keep a link to the sanitized source; mark any transformations in the research record. Honor requests to retain named content or chronology.
- **Mixed version:** retain the chosen source details and add generated material where it strengthens the defined case. Make the boundary identifiable in `evidence.md` by fact id or a grouped set of claims; an entire generated role may share one provenance entry.
- **Wholly generated version:** construct a coherent candidate across history, skills, education, credentials, and achievements. Label the source set synthetic in the research records rather than pretending it came from an interview or certificate.

Write achievement-led content with specific action, context, responsibility, and plausible impact. Generated metrics may be exact: keep units, periods, denominators, baselines, and arithmetic consistent with the role's scale and chronology. For example, an explicitly synthetic administrative case could say “Introduced a triage queue that reduced average request processing time from 3.0 to 2.1 days over six months.” The research record identifies this as generated scenario content, not a measured field result. Check related claims agree across the summary, bullets, skills, and variants. Use varied, natural language and concrete work rather than filling the page with keywords or inflated adjectives.

Preserve general professional breadth when requested; emphasize the exact role when that is the test. A blended or generated history still needs a credible progression, appropriate seniority, compatible tools and dates, and enough specific evidence under its important roles. Deliberately unrealistic or contradictory cases belong only to a test explicitly designed to examine those conditions.

## Keep provenance outside the blinded artifact

Store content in the research candidate's existing `facts.yaml`; select it with ordinary variants. In `evidence.md`, identify supplied, adapted, and generated claim groups and their sources or construction assumptions. The guide holds the test purpose, authorization scope, criteria, and material content choices. These are prose in existing records; the existing frontmatter `generated` flag continues to mean renderer-generated.

Intentionally invented content needs no pretend personal verification or repeated per-claim approval. Use `confirm` and manual `review` for genuine unresolved questions about the case, design, source-use permission, or intended test delivery. Do not clear an existing hold unrelated to fictional content merely because research mode is active. Approval means approved for this synthetic test, never verified real employment history.

For an agreed blinded test, produce an ordinary polished candidate resume: never put synthetic, fictional, research, or AI-generation labels/disclaimers in its rendered content, headers, filename, or exposed metadata. Record its synthetic identity internally. Use realistic, consistent names, organizations, dates, and approved test contact details; obvious placeholders can change parser behavior. Handle neutral filenames/metadata symmetrically across arms. Keep provenance, variant labels, expected winners, and writer rationale outside the tested input and reviewers' accessible context, linked by neutral internal identifiers. The company or organizer agrees to blinding; the system or human panel need not see provenance. Normal recipient and file checks still apply.

## Build, review, and stop

Keep the existing creation/build flow and use several purposeful revision stages: research and draft; review content against the criteria and revise; build and inspect extraction/layout, then correct delivery defects. Use `variant new --no-build`, source edits, review builds with `build-resumes --out`, and `./resumes check`. Review synthetic claims for design fit, source-retention fidelity, internal consistency, metric arithmetic, completeness, and intended blinding rather than asking whether invented duties really happened. Revisit research after draft review or authorized test feedback when it exposes a material missing criterion or contradiction; retain the tested version before revising.

Follow the destination's actual file rules and current vendor guidance. Use clear headings, legible text, and unambiguous employer/title/date relationships; check every delivered format's extraction and rendered pages. Local extraction and an `ats: safe` theme are useful checks, not proof of a target system's parsing or ranking. Use no hidden text or instructions intended to manipulate the screener. Resolve material defects and stop when the agreed criteria and checks are satisfied or a specific remaining question blocks them; optional taste changes do not create an endless search for perfection.

Deliver the files with their research purpose and a link or reference to the accompanying guide. A ready research resume is ready only for its recorded use. External uploads or test applications require the user's explicit authorization for the agreed destinations and actions, under host rules. Use the normal application tools only within that bounded test; stop at its agreed endpoint rather than broadening the search, updating real career profiles, or scheduling more applications.

## When an evaluation is authorized

Use the existing guide and application records. Keep a dated, unmodified baseline and freeze each artifact/version before testing. Separate development cases and feedback from held-out employer/role cases. An exact posting can be an input to a frozen tailoring procedure, but held-out reviewer decisions and earlier outputs must not feed its revision; any reused feedback becomes development evidence. Keep held-out answers and artifacts out of candidate/judge research context.

Use the same cases for baseline and treatment. Hold the synthetic profile fixed when testing wording and wording fixed when testing layout. Changing qualifications and presentation together establishes only a bundled version difference. Retain job conditions, identity/contact conditions, relevant system settings/version, and the actual responses. Randomize or interleave presentation, swap order for pairwise model judgments, and repeat variable AI responses within the agreed scope. Use independent blinded human ratings; ask for hiring judgments before synthetic-detection questions, or use separate raters to avoid priming.

Define and report distinct outcomes: actual parser fields correctly extracted or misattributed; shortlist/rank decisions under a fixed rubric; and human synthetic-detection judgments. Keyword scores and local extraction are diagnostics, not employer selection results. Test actual autofill only on agreed, authorized routes. Specify whether detectability concerns invented history, AI-written prose, or both. Detection accuracy or false-positive rates need an authorized genuine/control comparison; with only synthetic cases, report the synthetic-flag rate instead.

Check the scoring method on known reference cases and human-reviewed outputs before relying on model judges. Report AI and human results separately, including case and attempt denominators, paired differences, ties/failures, and uncertainty the sample supports. Repeated calls and reposts do not become independent cases. One successful screen cannot establish selection every time or human indistinguishability. Keep generated career metrics separate from actual test performance. Revise against material findings within the agreed stopping condition, then report gains, regressions, and untested cases; a failure is not permission for unlimited retries. These observations do not by themselves prove general recruiter accuracy, fairness, or universal ATS compatibility.

## Evaluation references

- [Greenhouse's parser guidance](https://support.greenhouse.io/hc/en-us/articles/200989175-Unsuccessful-resume-parse) documents missing fields caused by obvious placeholder names, employers, or titles. Realistic fixtures and field-level checks help separate this failure from a content-quality comparison.
- [NIST AI RMF, MEASURE](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/) calls for documented test sets, metrics, tools, deployment-relevant conditions, appropriate human evaluation, and generalization limits. Using those principles does not establish comprehensive validation or compliance.
- [Anthropic's statistical evaluation guidance](https://www.anthropic.com/research/statistical-approach-to-model-evals) explains paired comparisons, repeated responses, related-case dependence, and uncertainty. Count cases and repeated attempts separately.
- [Zheng et al., Judging LLM-as-a-Judge](https://arxiv.org/abs/2306.05685) examines position, verbosity, and self-enhancement biases. Neutral framing, order checks, and human-reviewed reference outputs help assess a judge; the study's benchmark results do not establish recruiter performance.

These sources inform evaluation design, not a proven resume formula. File checks and instruction review do not substitute for comparative trials when claiming an improvement in agent behavior or screening outcomes.
